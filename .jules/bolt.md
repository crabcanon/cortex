## 2024-05-24 - Efficient Next Sequence Number Calculation with SQL Aggregation
**Learning:** Found an anti-pattern across multiple services where determining the next sequence number for job events involved loading up to 1000 previous events into memory using `list_for_job(... limit=1000)` and extracting the last sequence number (`existing_events[-1].sequence_no`). This approach scales poorly as it fetches unnecessary data causing N+1 query-like inefficiencies and wasting memory/network resources. It violates best practices for large record retrieval.
**Action:** Implemented a new `get_max_sequence_no` method in `JobEventRepository` leveraging SQL aggregation directly: `select(func.coalesce(func.max(JobEventModel.sequence_no), 0))`. This allows the DB to efficiently compute the max in O(1) space/network, retrieving only a single integer. When calculating next sequence IDs or maximums in repositories, always prefer native SQL aggregation (`func.max`, `func.count`, etc) over retrieving and processing arrays in Python.
